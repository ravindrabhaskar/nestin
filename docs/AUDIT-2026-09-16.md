# NestIn — 360° Product & Engineering Audit

**Date:** 16 September 2026 · **Scope:** entire repository as of commit `c1f1606` (frontend, backend, data, security, DevOps, tests, UX) · **Outcome:** findings below were used to drive a rebuild of the backend and a re-wiring of the frontend in the same change set. Each finding is marked **Fixed**, **Partially fixed**, or **Open (roadmap)**.

---

## 1. Executive summary

NestIn had a polished, feature-rich React frontend (~33k lines: marketplace, tenant portal, owner CRM, staff RBAC, super-admin console) sitting on top of a backend that did not actually exist as a product:

- Every business object (properties, leads, bookings, customers, roles, staff, tenant bookings/payments/documents/tickets) lived in **browser `localStorage`** seeded from static TypeScript files. Nothing was shared between users, devices, or sessions; a tenant's booking never reached the owner's CRM; refreshing in another browser showed different data.
- The `services/` "microservices" were **in-memory mocks** with a data model unrelated to the frontend's, reachable only for auth. Docker Compose referenced 12 containers, 9 of which had no Dockerfile.
- Authentication had **critical, exploitable flaws** (see §3): unsigned tokens accepted, any email containing "admin" auto-provisioned as super-admin, hard-coded backdoor passwords, role escalation through profile update, fake Google login with a hard-coded personal email.
- Two half-implemented auth stacks (Supabase + custom JWT) coexisted; personal identities of the original author were hard-coded throughout the UI and seed data.

**After this change set:** a single, real API server (Express + built-in SQLite, zero native dependencies) persists every domain object per owner tenancy, enforces authorization on the server, runs the cross-entity workflows (booking → bed allocation → customer → payment → notifications), seeds a complete demo workspace including a 242-listing marketplace, and is covered by 23 API integration tests and 9 browser journeys. The frontend keeps its UI and context APIs but now reads/writes through the API with optimistic updates and rollback.

## 2. Architecture review

| Area | Before | After |
|---|---|---|
| Persistence | `localStorage` per browser; in-memory maps on the server | SQLite via Node's built-in `node:sqlite` (WAL mode). JSON-document collections with indexed columns (`owner_id`, `tenant_id`, `status`, …) plus relational `users`/`sessions`. File-backed with a Docker volume; in-memory for tests. |
| API surface | 12 mock routers, incompatible shapes | `/api/v1/{auth,properties,crm,rbac,tenant,admin,public,audit}` — 70+ endpoints, uniform `{success,data,error,metadata}` envelope, correlation IDs, rate limits, gzip. |
| Domain model | Duplicated and divergent between client and server | The frontend's `src/types/*` are the shared contract; the server imports them. Seed data lives in `src/data` and is only used by the server. |
| Workflows | Client-side only (e.g. approving a booking mutated local state) | Server-owned transactions: booking approval reserves the bed, creates/links the customer, records the payment, converts the lead, notifies both parties, and appends to the audit trail — atomically. |
| Auth | Custom HS256 with unsafe fallbacks; Supabase leftovers | scrypt password hashes, strict HS256 JWT bound to a revocable server session, Google Identity Services verified server-side, super-admin console with access code, per-employee RBAC resolved on every request. |
| Frontend data layer | Contexts read/write `localStorage` | Same context APIs (so 60+ components are unchanged) backed by the API: snapshot on login, optimistic mutations with rollback, server-authoritative results applied on response, background failures surfaced via a toast bus. |
| Deployment | Broken multi-container compose | One image (multi-stage Dockerfile, non-root, healthcheck), `docker-compose.yml`, `.env.example`, GitHub Actions CI (typecheck → API tests → build → e2e). |

**Design decision worth calling out:** a document store on SQLite rather than a 40-table relational schema. The frontend's aggregates (a property with rooms → beds, a customer with documents/payments/timeline) are deeply nested and already well-typed; storing them as JSON with extracted index columns keeps one source of truth, makes ownership checks trivial, and lets the schema evolve without migrations. The relational parts that matter for security (users, sessions) are proper tables. Moving to Postgres later is a change to `server/db/database.ts` (JSONB works identically).

## 3. Security findings

| # | Severity | Finding | Status |
|---|---|---|---|
| S1 | **Critical** | `parseJwtPayload` in shared middleware accepted any base64/JWT without signature verification, and fell back to `{ id: token, role: "owner" }` for any plain string — **any string was a valid owner token**. | **Fixed.** Tokens must carry a valid HS256 signature (timing-safe compare), a non-expired `exp`, `alg` must be `HS256`, and the session referenced by `sid` must exist and not be revoked. |
| S2 | **Critical** | `verifyJwt` accepted any signature starting with `sig-` ("backward compatibility"). | **Fixed** (removed). |
| S3 | **Critical** | `/auth/login` auto-provisioned unknown emails; emails containing `admin` became `super_admin`, `owner`/`paritala` became owners. No password required. | **Fixed.** Login requires a password; unknown users get the same 401 as wrong passwords; accounts are only created via `/auth/register` (tenant/owner only) or by an owner (staff) / operator (admin). |
| S4 | **Critical** | Hard-coded backdoor passwords (`NestIn@2026`, `Admin@NestIn2026`) accepted for **every** account; users without a hash accepted **any** password. | **Fixed.** scrypt hashes only; Google accounts have no password and cannot log in with one. |
| S5 | **High** | `PUT /auth/profile` merged the raw body into the user, allowing `role`, `email`, `ownerId`, `permissions` to be set by the caller. | **Fixed.** Whitelisted profile fields only. |
| S6 | **High** | "Google login" posted a hard-coded email; the server trusted `email` from the body and created/logged in that user. | **Fixed.** Client obtains an ID token from Google Identity Services; server verifies it with Google (audience, `email_verified`, expiry). Disabled with a clear message until `GOOGLE_CLIENT_ID` is configured. |
| S7 | **High** | JWT secret defaulted to a published string; `JWT_SECRET` and admin credentials were committed in `docker-compose.yml`. | **Fixed.** Production refuses to start without a ≥32-char `JWT_SECRET` and admin credentials; compose uses `${VAR:?}` so secrets come from `.env`. |
| S8 | **High** | Admin console pre-filled real admin password and access code in the login form ("Auto-fill Administrator Keys"). | **Fixed** (removed). |
| S9 | **High** | No session revocation: logout only deleted an in-memory map entry; tokens remained valid after "logout", password change, or staff deactivation. | **Fixed.** Sessions table; logout/revoke/password change/deactivation/suspension invalidate immediately; users can list and revoke devices. |
| S10 | **Medium** | CORS `Access-Control-Allow-Origin: *` with `Allow-Credentials: true`; token also accepted from `?token=` query string (leaks into logs). | **Fixed.** Same-origin by default, explicit `CORS_ORIGINS` allow-list, bearer header only. |
| S11 | **Medium** | No rate limiting or brute-force protection on auth. | **Fixed.** Per-IP+email limiter on auth routes, per-IP limiter on the API, per-IP limiter on public forms. |
| S12 | **Medium** | Signed document download URLs were unsigned (base64 JSON with expiry; trivially forged). | **Fixed by removal**; documents are metadata records scoped to the tenant/owner. Binary storage is on the roadmap (§8). |
| S13 | **Medium** | Payment webhook accepted unsigned events. | **Partially fixed**: the mock webhook was removed; Razorpay integration (with signature verification) is on the roadmap. Online payments are recorded as *simulated* until keys are set and the response says so. |
| S14 | **Medium** | No security headers, no body size limits (10 MB JSON), no input validation on most routes. | **Fixed.** `nosniff`, `DENY` framing, referrer policy, HSTS in production, 2 MB JSON limit, 512 KB per document, validation on every write. |
| S15 | **Low** | Audit "trail" lived in memory and was lost on restart. | **Fixed.** `audit_events` table; every domain event is persisted with actor, owner scope and correlation ID; exposed to owners (their scope) and admins (global). |
| S16 | **Low** | Real personal email addresses and names hard-coded in code and seed data. | **Fixed.** Mapped to `owner@nestin.com` / `tenant@nestin.com` / `staff@nestin.com` demo identities; UI defaults derive from the signed-in user. |

## 4. Backend / data findings

| # | Finding | Status |
|---|---|---|
| B1 | Backend data model (12 mock services) did not match the frontend's; the UI never called 90% of it. | **Fixed** — rebuilt around the frontend types. |
| B2 | Seed data was internally inconsistent: CRM bookings referenced properties (`prop-ist-gachibowli`, `prop-stanza-koramangala`) and beds (`room-101/bed-101-a`) that did not exist; a "Confirmed" booking pointed at a bed marked free. | **Fixed** — the seeder remaps records onto real inventory and marks beds occupied for confirmed bookings/active customers, so server integrity checks hold. |
| B3 | Tenant "My Bookings/Payments/Documents/Support" were independent `localStorage` lists unrelated to the CRM. | **Fixed** — tenant views are projections of the same booking/payment/document/ticket records the owner sees. |
| B4 | The 242 marketplace listings were generated in the browser and could not be booked (no backend record). | **Fixed** — seeded as published listings under a `marketplace@nestin.com` owner; every listing is real, bookable, and appears in admin stats. |
| B5 | No bed-level concurrency control (two tenants could "book" the same bed). | **Fixed** — booking creation checks bed occupancy *and* active bookings for that bed inside a SQLite `BEGIN IMMEDIATE` transaction; second request receives 409. |
| B6 | No idempotency on payments. | **Fixed** — `idempotencyKey` unique column; duplicate requests return the original record. |
| B7 | Owner could publish their own listing and self-assign "NestIn Verified" / caretaker verification badges. | **Fixed** — status transitions are workflow-controlled (draft → pending_approval via submit gate at ≥70% completeness → published/rejected by admin); editing a live listing's core content sends it back to review. |
| B8 | Public property endpoint exposed owner email, documents, caretaker private contacts and bed occupant names. | **Fixed** — `toPublicListing` redacts; catalogue endpoint returns a trimmed card projection (2.8 MB → ~1.2 MB raw, ~60 KB gzipped for 242 listings). |
| B9 | `express.static` served in production with `app.get("*")` before the API 404 handler order issues; no compression. | **Fixed** — API mounted first, gzip, long-cache immutable assets, no-cache `index.html`. |
| B10 | Docker Compose referenced 9 non-existent Dockerfiles; `services/auth/Dockerfile` copied a non-existent entrypoint. | **Fixed** — single image + compose. |

## 7. UX & product review (what works well, what to improve)

**Strengths:** coherent design system (Tailwind + Manrope/Inter, lime accent), strong owner-side information architecture (dashboard → leads → visitors → bookings → customers → properties → reports → staff/roles), rich listing pages, a complete RBAC permission catalogue (45 permissions across 6 groups) with per-employee overrides and an audit log, and thoughtful empty states.

**Improvements made in this pass:** real feedback on every action (loading, error, rollback toasts), staff logins created automatically with a one-time temporary password, demo-account shortcuts in the auth modal (only when the server runs in demo mode), re-verification notice when a live listing is edited.

**Recommended next (not done):** owner-side notifications centre wired to `/crm/notifications` polling or SSE; tenant document *file* upload; owner replies to tenant support tickets; rent-due reminders (a scheduled job over `customers` + `payments`); a proper listing search index (city/locality/rent facets are computed client-side over the full catalogue today — fine at 250 listings, not at 25,000).

## 11. Hardening pass (19 Sep 2026)

A second full sweep after the v3.1 change set. Toolchain was green (typecheck, 39 API tests, 13 e2e, build, `npm audit`) but a code review found the items below. All are fixed in this change set, and each has a guard so it cannot come back silently.

| # | Severity | Finding | Fix | Guard |
|---|---|---|---|---|
| H1 | High | `docker-compose.yml` defaulted `SEED_DEMO_DATA=true` + `DEMO_PASSWORD=NestIn@2026`, so a production deployment shipped the documented demo accounts. | `SEED_DEMO_DATA` is opt-in when `NODE_ENV=production`; compose defaults to `false`. | `assertProductionConfig()` refuses to boot with demo data on the default password (API test + CI step). |
| H2 | High | Without Razorpay keys every checkout (rent, deposit, subscription) was recorded as a *simulated success* — in production too. Owners could activate paid plans for free. | `assertPaymentsAvailable()` on every checkout entry point → 503 `PAYMENTS_UNAVAILABLE`. Simulation is only allowed outside production or with `ALLOW_SIMULATED_PAYMENTS=true` (staging). | Production refuses to start without gateway keys or the explicit flag; API test covers the 503. |
| H3 | High | Super-admin login always triggered two 403s (`/rbac/snapshot`, `/crm/snapshot`) and error toasts, because the owner-scoped contexts fetched for admins too. | Contexts only fetch for owners/employees. | e2e test asserts the admin console loads with zero 403 responses. |
| H4 | Medium | Security headers only applied under `/api`; the SPA document had no CSP, HSTS or frame protection while the JWT lives in `localStorage`. | `securityHeaders` is app-wide; a strict CSP (`script-src 'self'` + Google/Razorpay SDKs, `frame-ancestors 'none'`, `object-src 'none'`). | API test checks headers on API and non-API routes; e2e test fails on any CSP violation in the console. |
| H5 | Medium | `@iconify/react` fetched icon SVGs from `api.iconify.design` on every page load (found by the CSP guard). | `Icon` now maps to statically imported `lucide-react` components; dependency removed. | Same CSP e2e guard. |
| H6 | Medium | MRR counted an annual plan's full yearly price every month. | `yearlyPrice / 12`. | API test. |
| H7 | Medium | Invoice/booking/ticket numbers were 4–6 random digits (collisions; GST invoices must be consecutive). | `nextSequence()` counters in `meta`; invoices are `INV-2026-27-000042` per financial year; tickets `TKT-…`, bookings `NST-…`. | API test for uniqueness and FY rollover. |
| H8 | Medium | Webhook `payment.captured` marked records Paid without checking the captured amount. | Amount (paise) and currency must match; mismatches emit `WebhookAmountMismatch`. | API test. |

**Still open (deliberately):** the Find PG page facets client-side over the full catalogue (§10). Moving it to `GET /properties/public` needs gender/food/amenity/room-type/rating columns in the SQL search and a rewrite of the page's filter model — a feature, not a fix. Fine below ~1,000 listings.

**How the guards work together:** `npm run check` (typecheck → lint → format) runs in the pre-commit hook and in CI; CI additionally fails on CRLF files and proves the production config guard refuses to start without secrets; `tests/api/hardening.test.ts` pins every behavioural fix; the e2e suite fails on CSP violations or admin 403s.
